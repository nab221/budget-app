# Milestone Roadmap: Local File Persistence (v1.4)

Milestone Goal: Enable users to sync their IndexedDB budget data with a local file on their computer via the File System Access API, ensuring persistent storage and easy backups.

## Phases

- [ ] **Phase 1: Database Mutation Refactoring** - Consolidate all database writes to the repository layer for centralized sync triggers.
- [ ] **Phase 2: File System Handle Utility** - Implement handle persistence and permission lifecycle management.
- [ ] **Phase 3: Auto-save & Sync Logic** - Implement debounced background sync with resilience for cloud-synced folders.
- [ ] **Phase 4: File Persistence UI** - Add UI for file selection, status monitoring, and re-authorization.
- [ ] **Phase 5: Documentation & Validation** - Update README, document browser compatibility, and verify end-to-end reliability.

## Phase Details

### Phase 1: Database Mutation Refactoring
**Goal**: Centralize all database mutations in the repository layer to ensure consistent sync triggers.
**Depends on**: Nothing
**Requirements**: REPO-01, REPO-02, REPO-03
**Success Criteria** (what must be TRUE):
  1. All `db.table.add/put/delete` calls in `budget-app.html` are replaced with `Repository` method calls.
  2. The `Repository` layer emits a "mutation" event or call for every write operation.
  3. App functionality remains identical after refactoring (manual smoke test).
**Plans**: TBD

### Phase 2: File System Handle Utility
**Goal**: Securely pick and persist file handles to allow seamless sync across browser sessions.
**Depends on**: Phase 1
**Requirements**: FS-01, FS-02, FS-03, FS-04
**Success Criteria** (what must be TRUE):
  1. User can pick a file from their local disk using a "Select File" dialog.
  2. The file handle is successfully persisted in IndexedDB and survives page reloads.
  3. App can query and request permissions for a persisted handle on load.
**Plans**: TBD

### Phase 3: Auto-save & Sync Logic
**Goal**: Automatically sync budget data to the selected local file without blocking the user.
**Depends on**: Phase 2
**Requirements**: SYNC-01, SYNC-02, SYNC-03, SYNC-04
**Success Criteria** (what must be TRUE):
  1. Every mutation triggers a background save after a 2-second debounce period.
  2. Saving does not lock the UI or cause visible performance lag.
  3. If a file is locked by OneDrive/Dropbox, the app retries with exponential backoff rather than failing immediately.
  4. The local file contains the latest encrypted/JSON budget data after a sync completes.
**Plans**: TBD

### Phase 4: File Persistence UI
**Goal**: Provide clear visibility and control over the file sync status to the user.
**Depends on**: Phase 3
**Requirements**: UI-01, UI-02, UI-03, UI-04
**Success Criteria** (what must be TRUE):
  1. A "Local File Sync" status is visible in the settings/backup section.
  2. User can see "Synced", "Saving...", or "Error" status in real-time.
  3. User can manually re-connect a disconnected handle with a single button click.
  4. A toast notification appears if a background sync fails persistently.
**Plans**: TBD

### Phase 5: Documentation & Validation
**Goal**: Ensure the feature is well-documented and verified for production use.
**Depends on**: Phase 4
**Requirements**: DOCS-01, DOCS-02, VAL-01, VAL-02
**Success Criteria** (what must be TRUE):
  1. README contains clear instructions on how to set up local file sync.
  2. Browser compatibility (Chromium-only) is clearly noted for the user.
  3. Data is verified to be consistent between IndexedDB and the local file after multiple sessions.
  4. Existing cloud backup features (GDrive/OneDrive) are verified to still work correctly.
**Plans**: TBD
