## Summary

Phase 39.1 is a pure UI phase. The database schema (`incomeSources`, schema v21), the repository (`incomeSourceRepository` with `getAll`, `getActive`, `validateAndAdd`, `validateAndUpdate`, `delete`), and the projection utilities (`getNextIncomeEvent`, `getUpcomingIncomeEvents` in `src/utils/income.js`) are all complete and tested. The task is to build a new `src/ui/income-sources.js` module and wire it into the app the same way `childcare.js` was wired in.

The confirm/adjust flow (pending income → confirmed income transaction) requires: (1) a "pending confirmations" section at the top of the tab driven by `getUpcomingIncomeEvents`, (2) a confirm action that calls `incomeRepository.add(...)` to write a real income transaction, and (3) an optional amount-edit step before confirming. This mirrors exactly how `confirmMarkPaid` in `debts.js` writes a payment into `recurrentExpenses` when the user confirms a suggested credit card payment.

The Settings cleanup is straightforward: remove the call to `_renderSourcesSection` and its event-binding from `incomeSpendingSettings.render()` and `_bindSourceEvents`. The Spending Buckets section in Settings is retained.

**Primary recommendation:** Create `src/ui/income-sources.js` as a self-contained module mirroring `childcare.js` structure; wire navigation and `renderAll` exactly as `childcareUI` is wired; remove income-source rendering from `incomeSpendingSettings`.

## Architecture Patterns

### Recommended Module Structure
```
src/ui/income-sources.js   — new module (CRUD list + confirm flow)
src/ui/income-spending-settings.js  — remove income source section only
src/app.js                 — add incomeSourcesUI import + init + renderAll wiring
index.html                 — add nav tab button + tab-panel div
```

### Pattern 1: Tab Module Shape (matches childcareUI / debtUI)
**What:** ES module object exported as `incomeSourcesUI` with `init()` and `render()` methods.
**When to use:** Every tab UI in this project follows this pattern.
**Example from `childcare.js`:**
```javascript
export const incomeSourcesUI = {
  async init() {
    this._bindEvents();
    window.addEventListener('app:refresh', () => this.render());
    await this.render();
  },
  async render() {
    // load data → build HTML → inject into container → bind dynamic events
  }
};
```

### Pattern 2: Inline Form (matches income-spending-settings.js pattern)
**What:** The add/edit form is rendered inline below the table, not in a modal.
**When to use:** `income-spending-settings.js` already contains `_incomeSourceForm()` — this function can be re-used verbatim or adapted in the new module.
**Key detail:** The form includes `isf-rule` → `isf-day-wrapper` visibility toggle for `nth-of-month` rule. This logic is tested and known-good.

### Pattern 3: Confirm/Adjust Card (analogous to debts.js `showMarkPaidPrompt`)
**What:** Each upcoming income event from `getUpcomingIncomeEvents()` renders a pending card. User presses "Confirm" (one tap, accepts expected amount) or "Adjust" (edits amount field, then confirms). On confirm: call `incomeRepository.add({ date, source: sourceName, amount: actualPounds, categoryId: null })`.
**When to use:** Shown at the top of the tab as a "To confirm" section when any upcoming events exist within the current pay period or past due.
**Example flow:**
```javascript
// Source: analogous to debts.js confirmMarkPaid
const event = getUpcomingIncomeEvents(activeSources, todayStr(), 5);
// For each event, render a card:
// "Expected £X from [sourceName] on [adjustedDate]"
// [Confirm] [Adjust amount]

// On confirm:
await incomeRepository.add({
  date: event.adjustedDate,
  source: event.sourceName,
  amount: fromPence(event.amount),    // event.amount is in pence
  categoryId: null,
  isCleared: false,
  isReconciled: false
});
```

### Pattern 4: Tab Navigation Registration (matches app.js for childcare)
**What:** Add `incomeSourcesUI` to:
1. `import` in `app.js`
2. `renderAll()` switch block: `if (panelId === 'income-sources') renderTasks.push(incomeSourcesUI.render());`
3. `init()` parallel block: `incomeSourcesUI.init()`

**index.html — nav tab addition:**
```html
<button class="tab" data-tab="income-sources" aria-label="Income Sources">
  <span class="tab-label">Income</span>
</button>
```

**index.html — panel div addition (alongside other panels):**
```html
<div class="tab-panel" data-panel="income-sources">
  <div id="incomeSourcesSummary"></div>
  <div id="incomePendingConfirmations"></div>
  <div id="incomeSourceList"></div>
</div>
```

### Pattern 5: Settings Cleanup
**What:** Remove the income-source portion from `incomeSpendingSettings` while keeping Spending Buckets.
**What to remove:**
- In `render()`: remove `incomeSourceRepository.getAll()` call; remove `_renderSourcesSection(sources)` concatenation; remove `this._bindSourceEvents(container, sources)` call.
- Remove `_bindSourceEvents()` method and `_bindSourceFormEvents()` method.
- Remove `_renderSourceRow()` and `_renderSourcesSection()` functions.
- Remove `_incomeSourceForm()` function (or move to new module if reusing it).
- Remove `incomeSourceRepository` import (no longer needed here).

**What to keep:** All spending-bucket functions, `spendingBucketRepository` import, `getNextIncomeEvent` import if still needed (it won't be — remove it too).

### Anti-Patterns to Avoid
- **Double safeHTML nesting:** Badge HTML must be plain strings inside an outer `safeHTML` template literal. Never call `safeHTML` inside another `safeHTML` call. (Known project pitfall from Phase 09 TFC badge bug.)
- **Reading non-transaction tables inside Dexie transactions:** Do not call `incomeSourceRepository.getAll()` inside a `db.transaction('rw', [db.income], ...)` block. The `db.incomeSources` table would not be in scope. (Known pitfall from Phase 09 DexieError.)
- **Event listener accumulation:** Use `.onclick = ...` assignment rather than `.addEventListener(...)` for buttons that get re-rendered. (Pattern from 27-01 decision log — `_renderSignedIn` uses `.onclick`; `income-spending-settings.js` already uses `.onclick` throughout.)
- **Global function leakage:** Avoid `window.confirmIncome = ...` style globals unless strictly necessary. The existing debts module uses them for `confirmMarkPaid` but newer modules (childcare) avoid them. Prefer binding inline event handlers via data attributes and event delegation on the container.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Next payday projection | Custom date math | `getNextIncomeEvent(source, todayStr())` | Already handles nth-of-month, last-day, last-working-day with banking-calendar adjustment |
| Banking-calendar adjustment | Weekend/holiday checks | `adjustedPaymentDate()` from `banking-calendar.js` | UK bank holidays, 14-iter safety guard, tested in 26 unit tests |
| Pence/pounds conversion | Manual `* 100` / `/ 100` | `toPence()` / `fromPence()` / `formatGBP()` | Established project convention, all amounts stored as integer pence |
| Modal dialog | Custom overlay | `modalUI.show(title, html, buttons)` from `render.js` | Shared, accessible, Esc-key wired |
| Toast notifications | Alert/console | `notificationUI.success/error/warning()` | Already wired, no extra setup needed |
| HTML escaping | Manual replace chain | `escHtml()` (already in `income-spending-settings.js`) or `safeHTML` tag | DOMPurify wrapper; never nest |
| Form date input formatting | Manual string splits | `new Date().toISOString().split('T')[0]` | Consistent YYYY-MM-DD throughout codebase |

## Common Pitfalls

### Pitfall 1: pence vs pounds in incomeRepository.add()
**What goes wrong:** `incomeRepository.add()` passes the amount through `toPence()` internally (via `createBaseRepository(db.income, ['amount'])`). If the caller already passes pence, the value gets doubled.
**Why it happens:** The `createBaseRepository` pence-fields list runs `toPence(value)` unconditionally on the `amount` field.
**How to avoid:** Always pass pounds (e.g. `fromPence(event.amount)`) to `incomeRepository.add()`. The event object from `getUpcomingIncomeEvents` returns `amount` in pence (stored value from `incomeSources.monthlyAmount`).
**Warning signs:** Income entries appear with amounts 100x larger than expected.

### Pitfall 2: monthlyAmount stored raw as pence in incomeSources
**What goes wrong:** `incomeSourceRepository` uses `createBaseRepository(db.incomeSources, [])` — no pence-field conversion. The amount is stored as the raw value passed in. The settings UI passes pence directly (`strToPence(form.querySelector('#isf-amount')?.value)`) and reads it back with `penceToStr`.
**Why it happens:** This was a Phase 33 decision: "monthlyAmount stored as raw pence (no double-conversion)".
**How to avoid:** The new tab's add/edit form must continue this convention: convert £ → pence before calling `validateAndAdd/validateAndUpdate`, and display pence ÷ 100 when showing the amount. Copy the `penceToStr`/`strToPence` helpers from `income-spending-settings.js` into the new module.
**Warning signs:** Amounts in the income sources list appear as £0.xx instead of £XXX.xx.

### Pitfall 3: getUpcomingIncomeEvents returns future events, not this-cycle events
**What goes wrong:** The function returns events strictly *after* `fromDate`. If called with today's date, it may return next month's payday even though this month's hasn't been confirmed yet.
**Why it happens:** `getNextIncomeEvent` has an `if (nominal > from)` strict greater-than check (not `>=`).
**How to avoid:** To find "current cycle" pending events, call with `fromDate` set to the day *before* the expected payday (e.g. 1 day before the 25th). Or: call with the start of the current pay period as `fromDate`. Simplest approach: call `getUpcomingIncomeEvents(sources, startOfLastMonth(), 10)` and filter results where `adjustedDate <= endOfCurrentPayPeriod`.
**Warning signs:** No pending confirmations are ever shown even when sources exist.

### Pitfall 4: Settings container not found on render
**What goes wrong:** `incomeSpendingSettings.render()` is a no-op if `#incomeSpendingSettingsContainer` is not in the DOM. After removing the income-source section, a brief period during implementation may leave the Settings panel partially broken.
**How to avoid:** Remove the income-source HTML from the Settings panel in `index.html` in the same commit where `_renderSourcesSection` is removed from `incomeSpendingSettings.render()`. The two changes are atomic.

### Pitfall 5: Tab navigation `data-tab` mismatch
**What goes wrong:** If `index.html` nav button uses `data-tab="income-sources"` but `app.js` `renderAll()` checks for `panelId === 'incomeSources'`, the tab renders blank.
**How to avoid:** Keep `data-tab` and `data-panel` values consistent (use `income-sources` with hyphen throughout). The `app.js` check must read `panelId === 'income-sources'`.

## Open Questions

1. **Which income events to surface in the pending-confirmation section?**
   - What we know: `getUpcomingIncomeEvents(sources, fromDate, limit)` returns future events sorted by adjustedDate.
   - What's unclear: Should the confirmation section show only events whose `adjustedDate` is within the current pay period, or all past-due + current-period events?
   - Recommendation: Show events where `adjustedDate <= today + 7 days` AND `adjustedDate >= startOf(current pay period)`. Use `todayStr()` minus 45 days as the lower bound to catch any past-due unconfirmed items. This is Claude's discretion — lock during planning.

2. **Tab label**
   - Options: "Income Sources", "Income" (conflicts with existing Income tab), "Pay Sources", "Paydays"
   - Recommendation: "Pay Sources" avoids collision with the existing Income tab label, is concise, and fits the bottom bar truncation rules (6 chars = "Pay So" or icon-only at 360px). Claude's discretion — lock during planning.

3. **Pending confirmation badge on tab**
   - What we know: Other tabs do not show badge counts. The tab bar CSS supports `.tab` buttons with `<span class="tab-label">`.
   - Recommendation: Add a small numeric badge (styled like `badge-red` used elsewhere) to the tab button when there are unconfirmed events. Optional — Claude's discretion.
