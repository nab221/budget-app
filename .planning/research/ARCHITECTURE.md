### Structure Rationale

- **db/**: Single file exports the shared Dexie instance. Nothing outside this folder touches IndexedDB directly — all other code calls db methods through service functions. This makes the data layer replaceable and testable.
- **services/**: Pure business logic with no DOM access. Receives data, returns computed results. Can be unit-tested in isolation with mocked Dexie calls.
- **controllers/**: DOM interaction only. Call services, render results to DOM, bind event listeners. One controller per major tab view keeps files small.
- **utils/**: Shared stateless helpers. Date, format, validation, and constants live here to eliminate duplication across the monolith.
- **ui/**: Cross-cutting UI infrastructure (router, modal, theme) that is not domain-specific.

## Architectural Patterns

### Pattern 1: Data Layer Isolation (Repository Pattern)

**What:** All IndexedDB access goes through `db.js`. No controller or service calls `new Dexie()` or `db.table.add()` directly. Instead, service functions accept/return plain objects and call named functions from `db.js`.

**When to use:** Always. This is the foundation of the rebuild. The monolith fails precisely because DB calls are scattered everywhere.

**Trade-offs:** Small overhead of one indirection layer, but prevents the re-entrant query mess from the original codebase.

**Example:**
```javascript
// db/db.js — only place Dexie is touched
import Dexie from 'dexie';

export const db = new Dexie('BudgetApp');
db.version(1).stores({
  income:           '++id, date, source, amount',
  fixedSpends:      '++id, date, category, label, status, amount',
  variableSpends:   '++id, date, category, note, amount',
  subscriptions:    '++id, name, amount, frequency, nextDate, method',
  debts:            '++id, name, type, limit, apr, minRule, minValue, minFloor',
  statements:       '++id, debtId, month, openBal, closeBal',
  assets:           '++id, name, amount, currency, asOf',
  categories:       '++id, group, name',
  recurringTpls:    '++id, type, category, amount, frequency, nextDue',
  budgetTargets:    '++id, categoryId, monthlyTarget'
});

// services/budgetService.js — calls db, never uses Dexie directly
import { db } from '../db/db.js';

export async function getIncomeForPeriod(year, month) {
  const all = await db.income.orderBy('date').toArray();
  return all.filter(r => inRange(r.date, year, month));
}
```

### Pattern 2: Controller Owns DOM, Service Owns Logic

**What:** Controllers never compute business values. Services never touch the DOM. The boundary is enforced by file structure.

**When to use:** Every UI interaction. Controller reads form → calls service → renders result.

**Trade-offs:** More files than the monolith. Worth it — the original codebase has debt calculation logic inside `innerHTML` template literals.

**Example:**
```javascript
// controllers/debtsController.js
import { getDebts } from '../services/budgetService.js';
import { calcMinPayment } from '../services/payoffService.js';
import { £ } from '../utils/format.js';

export async function renderDebts() {
  const debts = await getDebts();
  const rows = debts.map(d => {
    const min = calcMinPayment(d);
    return `<tr>
      <td>${d.name}</td>
      <td data-id="${d.id}">${£(min)}</td>
      ...
    </tr>`;
  });
  document.getElementById('debts-tbody').innerHTML = rows.join('');
}
```

### Pattern 3: Event Delegation Over Inline Handlers

**What:** Attach one listener to a table parent element, read action and ID from `data-*` attributes. No `onclick=` in template strings.

**When to use:** All table/list renders where rows have delete/edit/open actions.

**Trade-offs:** Slightly less intuitive than inline handlers but eliminates XSS risk and the `window.del` global pattern from the monolith.

**Example:**
```javascript
document.getElementById('debts-table').addEventListener('click', async (e) => {
  const btn = e.target.closest('[data-action]');
  if (!btn) return;
  const { action, id } = btn.dataset;
  if (action === 'delete') await deleteDebt(Number(id));
  if (action === 'statement') openStmtModal(Number(id));
  await renderDebts();
});
```

### Pattern 4: Offline-First with Manual Sync

**What:** The app is fully functional with zero network. Cloud backup (Google Drive / Dropbox) is an opt-in, user-triggered action — not a background sync that blocks operation.

**When to use:** This entire app. It is local-first by design.

**Why not Background Sync API:** Background Sync has no Firefox/Safari support as of 2025. Manual sync avoids compatibility constraints and matches the project's stated goal of "Google Drive/Dropbox manual backup."

**Trade-offs:** No automatic cross-device sync. User must explicitly push/pull. Acceptable for the stated use case — "personal tool, used on known devices."

### Pattern 5: Dexie Schema Versioning

**What:** Every schema change uses a new `db.version(N)` block. Dexie runs upgrade functions sequentially on first open after update.

**When to use:** Any time a new table or index is added during the rebuild phases.

**Example:**
```javascript
db.version(1).stores({ /* initial schema */ });

// Phase 2 adds recurringTpls and budgetTargets:
db.version(2).stores({
  recurringTpls: '++id, type, category, amount, frequency, nextDue',
  budgetTargets: '++id, categoryId, monthlyTarget'
}).upgrade(tx => {
  // no data migration needed for new tables
});

// Phase N adds encrypted export flag:
db.version(3).stores({}).upgrade(async tx => {
  // migrate existing records if needed
});
```

## Dexie.js Schema Design

### Recommended Schema

```javascript
db.version(1).stores({
  // Indexed fields only: Dexie schema does NOT store all fields,
  // just the ones you need to query/filter by.
  // Non-indexed fields are stored automatically in the record object.

  income:        '++id, date',
  // Query by date for period filtering. source/amount not indexed (not queried).

  fixedSpends:   '++id, date, category, status',
  // Query by date AND category for budget targets. status for paid/pending filter.

  variableSpends:'++id, date, category',
  // Query by date and category.

  subscriptions: '++id, nextDate',
  // Query by nextDate for "due soon" alerts.

  debts:         '++id',
  // No secondary indexes needed — all debts always loaded together.

  statements:    '++id, debtId, month',
  // Query by debtId to get statement history for one debt. month for sort.

  assets:        '++id',
  // All assets always loaded together — no secondary index.

  categories:    '++id, group',
  // Query by group to populate typed dropdowns.

  recurringTpls: '++id, frequency, nextDue',
  // Query by nextDue to suggest auto-creation.

  budgetTargets: '++id, categoryId',
  // Query by categoryId for target lookup.
});
```

### Indexing Rules (HIGH confidence — from Dexie docs)

- Only index fields you will filter or sort by using `.where()` or `.orderBy()`.
- Do NOT index every field — IndexedDB indexes consume storage and slow writes.
- For compound queries (e.g., date AND category), use client-side filtering after fetching by the primary index. Dexie compound indexes exist but add complexity; client-side filter is simpler for a personal-scale app.
- Primary key `++id` (auto-increment integer) is correct for all tables here — no natural key exists.
- `month` in `statements` stores as `YYYY-MM` string. Sort lexicographically ascending, reverse to display descending. This fixes the existing sort bug.

### Critical IndexedDB Transaction Rule (HIGH confidence)

Never `await` a non-Dexie async operation inside a `db.transaction()` block. IndexedDB commits the transaction at the next microtask boundary. Mixing `fetch()` or `setTimeout` inside a Dexie transaction causes `TransactionInactiveError`. Do all non-DB async work before entering a transaction.

## PWA Service Worker Setup

### Recommended Approach: Vite + vite-plugin-pwa + Workbox

Use `vite-plugin-pwa` with `generateSW` strategy for the initial build. It auto-generates a service worker that precaches all built assets (HTML, CSS, JS, icons) and the Workbox runtime. Confidence: HIGH.

```javascript
// vite.config.js
import { defineConfig } from 'vite';
import { VitePWA } from 'vite-plugin-pwa';

export default defineConfig({
  plugins: [
    VitePWA({
      registerType: 'autoUpdate',
      workbox: {
        globPatterns: ['**/*.{js,css,html,ico,png,svg,woff2}'],
        // Cache-first for all precached assets (app shell)
        // Network-first not needed — this app has no API calls to cache
      },
      manifest: {
        name: 'Budget App',
        short_name: 'Budget',
        theme_color: '#1e293b',
        background_color: '#ffffff',
        display: 'standalone',
        start_url: '/',
        icons: [
          { src: 'icons/icon-192.png', sizes: '192x192', type: 'image/png' },
          { src: 'icons/icon-512.png', sizes: '512x512', type: 'image/png' },
          { src: 'icons/icon-512-maskable.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' }
        ]
      }
    })
  ]
});
```

### Caching Strategy

This app has no server API. All data is local. The only things to cache are static assets.

| Asset Type | Strategy | Rationale |
|------------|----------|-----------|
| App shell (HTML, CSS, JS) | Cache-first (precache) | Never changes mid-session; built assets have content hashes |
| CDN libs (if any remain) | Cache-first with expiry | pdfjs-dist should be bundled not CDN-loaded |
| Google/Dropbox OAuth calls | Network-only | Cannot cache auth redirects |

### Service Worker Registration

Register in `app.js` using the Workbox-generated helper. Do not manually write `navigator.serviceWorker.register()` — vite-plugin-pwa generates the registration snippet.

## Cloud Sync: Google Drive and Dropbox OAuth Flows

### The Core Problem for a Static File App

**Google Drive:** Google's OAuth2 for web applications technically requires a client_secret for the server-side code exchange. However, Google Identity Services (GIS) provides a **token model** (implicit-like flow) for client-side apps that issues short-lived access tokens without a backend. The token is not persisted by the browser — the user must re-authorize on each page load or when the token expires. Confidence: HIGH (verified against Google docs).

**Dropbox:** Dropbox explicitly supports PKCE for pure client-side JavaScript apps with no backend. Using PKCE with `token_access_type=offline`, you get a short-lived access token plus a refresh token. The refresh token can be stored in localStorage to avoid re-authorization. Confidence: HIGH (Dropbox dev docs verified).

### Recommended Implementation

**Prefer Dropbox as the primary sync target** because its PKCE flow is cleaner for a static app (refresh token persistence = no re-auth on every page load). Google Drive works but requires re-authorization each session.

**Google Drive — Token Model Flow:**
```javascript
// src/services/syncService.js
const tokenClient = google.accounts.oauth2.initTokenClient({
  client_id: 'YOUR_CLIENT_ID.apps.googleusercontent.com',
  scope: 'https://www.googleapis.com/auth/drive.appdata',
  callback: (tokenResponse) => {
    // Store token in memory only (not localStorage — expires in 1h)
    accessToken = tokenResponse.access_token;
  },
});

export function authorizeGoogleDrive() {
  tokenClient.requestAccessToken();
}

export async function uploadToGoogleDrive(jsonString) {
  // Upload to appDataFolder — only visible to this app, no user Drive clutter
  await fetch('https://www.googleapis.com/upload/drive/v3/files?uploadType=multipart', {
    method: 'POST',
    headers: { Authorization: `Bearer ${accessToken}` },
    body: buildMultipartBody('budget-backup.json', jsonString)
  });
}
```

Use `drive.appdata` scope (Application Data folder) — the backup file is hidden from the user's Drive UI, which is cleaner for a personal tool.

**Dropbox — PKCE Flow:**
```javascript
import { Dropbox } from 'dropbox';

const dbx = new Dropbox({ clientId: 'YOUR_APP_KEY' });

export async function startDropboxAuth() {
  const authUrl = await dbx.auth.getAuthenticationUrl(
    window.location.href,  // redirect back to app
    null,
    'code',                // authorization code flow
    'offline',             // request refresh token
    null, null,
    true                   // usePKCE
  );
  // Store code_verifier in sessionStorage before redirect
  sessionStorage.setItem('dropbox_cv', dbx.auth.codeVerifier);
  window.location.href = authUrl;
}

export async function handleDropboxCallback() {
  const params = new URLSearchParams(window.location.search);
  const code = params.get('code');
  if (!code) return;
  dbx.auth.setCodeVerifier(sessionStorage.getItem('dropbox_cv'));
  const token = await dbx.auth.getAccessTokenFromCode(window.location.href, code);
  // Store refresh token in localStorage for future sessions
  localStorage.setItem('dropbox_refresh', token.result.refresh_token);
}

export async function uploadToDropbox(jsonString) {
  await dbx.filesUpload({
    path: '/budget-backup.json',
    contents: new Blob([jsonString]),
    mode: { '.tag': 'overwrite' }
  });
}
```

### OAuth Limitations for a Static App

| Constraint | Google Drive | Dropbox |
|------------|-------------|---------|
| Client secret required | No (token model bypasses) | No (PKCE) |
| Token persists across page loads | No (must re-auth each session) | Yes (refresh token in localStorage) |
| Redirect URI restrictions | Exact match required in Console | Exact match required in App Console |
| Works on file:// protocol | No (OAuth requires https) | No (OAuth requires https) |
| Works on GitHub Pages | Yes | Yes |
| Offline operation | N/A (sync is always online) | N/A |

**Implication:** The app must be served over HTTPS (GitHub Pages satisfies this) for cloud sync to function. Local `file://` access works for everything except OAuth.

## PDF Parsing Pipeline

### Library: pdfjs-dist (Mozilla PDF.js, browser build)

Use `pdfjs-dist` directly in the browser — it is the same engine as the Firefox PDF viewer, runs client-side with no server, and provides per-item text content with `x`, `y` coordinates on the page. Confidence: MEDIUM (verified functionality; bank-specific heuristics are application-specific and must be tested empirically).

```javascript
// services/pdfParser.js
import * as pdfjsLib from 'pdfjs-dist';
pdfjsLib.GlobalWorkerOptions.workerSrc = new URL(
  'pdfjs-dist/build/pdf.worker.min.mjs',
  import.meta.url
).href;

export async function extractTextItems(file) {
  const arrayBuffer = await file.arrayBuffer();
  const pdf = await pdfjsLib.getDocument({ data: arrayBuffer }).promise;
  const allItems = [];
  for (let pageNum = 1; pageNum <= pdf.numPages; pageNum++) {
    const page = await pdf.getPage(pageNum);
    const content = await page.getTextContent();
    // Each item: { str, transform: [a,b,c,d,x,y], width, height }
    allItems.push(...content.items.map(item => ({
      text: item.str,
      x: item.transform[4],
      y: item.transform[5],
      page: pageNum,
    })));
  }
  return allItems;
}
```

### Pipeline Stages

```
PDF File (user drop/select)
    ↓
[Stage 1] Raw text extraction
    pdfjs-dist: text items with x,y coordinates per page

    ↓
[Stage 2] Bank detection
    Pattern-match header text against known bank signatures:
    - "Barclays Bank" → barclaysParser
    - "HSBC" → hsbcParser
    - "NatWest" / "National Westminster" → natwestParser
    - "Lloyds" → lloydsParser
    - "Santander" → santanderParser
    - No match → manualMappingUI

    ↓
[Stage 3] Column identification (bank-specific)
    Each parser identifies column x-ranges from header row:
    Date column: items with x < X_THRESHOLD_1
    Description: items with X_THRESHOLD_1 < x < X_THRESHOLD_2
    Amount/debit/credit: items near right margin

    ↓
[Stage 4] Row assembly
    Group items by approximate y-coordinate (within ±3px = same row)
    Sort by x within each row
    Assemble as { date, description, debit, credit }

    ↓
[Stage 5] Transaction normalisation
    Parse date strings to ISO format
    Parse amounts (strip £, commas, handle CR/DR suffixes)
    Categorise: match description keywords to existing categories

    ↓
[Stage 6] Preview + user confirm
    Show parsed transactions in a preview table
    User corrects categories, removes non-transactions (headers, totals)
    Confirm → bulk insert into variableSpends / fixedSpends
```

### Manual Fallback UI

When the bank parser cannot identify columns (unrecognised PDF layout), present a column-mapping interface:

- Display a sample of extracted text rows
- User drags or selects which column is Date / Description / Amount
- Parser re-runs with user-specified x-ranges
- Saves mapping profile keyed by bank header signature for future reuse

### PDF Parsing Pitfalls (MEDIUM confidence)

- UK bank PDFs are mostly text-based, not image scans. However, some statements (especially older HSBC) are image PDFs — pdfjs-dist returns empty text for those. Flag these to the user with "Unable to extract text from this PDF."
- Column x-coordinates vary across statement dates from the same bank — do not hard-code pixel values. Detect column positions from the header row each time.
- PDF.js worker must be served from same origin or configured with `workerSrc` — use Vite's `import.meta.url` pattern to resolve worker path correctly in the built bundle.

## Data Flow

### Primary Write Flow (add a transaction)

```
User fills form (date, category, amount)
    ↓
Controller validates input (validation.js)
    ↓
Controller calls service function (budgetService.addFixed)
    ↓
Service calls db.fixedSpends.add(record)
    ↓
Dexie writes to IndexedDB
    ↓
Controller calls renderFixed() + renderDashboard()
    ↓
DOM updated with new row + updated totals
```

### Primary Read Flow (render dashboard)

```
Month picker change event
    ↓
dashboardController reads period (year, month)
    ↓
Calls budgetService.getSummary(year, month)
    ↓
budgetService queries each table in parallel (Promise.all)
    ↓
Filters by period, computes totals and ratios
    ↓
Returns summary object
    ↓
dashboardController writes summary values to DOM
```

### Cloud Sync Flow (upload)

```
User clicks "Backup to Dropbox"
    ↓
syncService checks for stored refresh token
    ↓
If present: silently refresh access token
If absent: initiate PKCE auth flow (redirect → return)
    ↓
syncService exports all tables as JSON (same format as existing export)
    ↓
syncService uploads JSON to Dropbox /budget-backup.json (overwrite)
    ↓
UI shows success confirmation with timestamp
```

### PDF Import Flow

```
User drops PDF file
    ↓
pdfParser.extractTextItems(file)
    ↓
Detect bank from header text
    ↓
Run bank-specific parser or prompt manual column mapping
    ↓
Preview table shown to user
    ↓
User confirms/edits
    ↓
Bulk insert into variableSpends (or fixedSpends)
    ↓
renderVariable() + renderDashboard() refresh
```

## Suggested Build Order (Phase Dependencies)

The architecture has clear dependency layers that dictate build order:

1. **Foundation first — db.js and utils/**
   - Nothing can be built without the Dexie schema and shared utilities.
   - `constants.js` must exist before any business logic (eliminates magic numbers).
   - `date.js` and `format.js` are required by every controller.

2. **Data layer — services/ (no DOM dependency)**
   - `budgetService.js` and `payoffService.js` can be built and unit-tested before any UI.
   - Pure functions with Dexie calls — testable with minimal setup.

3. **Core UI — controllers/ for table stakes features**
   - Dashboard, income, fixed, variable, debts.
   - These replicate existing functionality — straightforward port from monolith.
   - Requires db, services, utils to be complete.

4. **Infrastructure — PWA, theme, router**
   - Service worker, manifest, tab routing — can be added once core UI works.
   - Vite build setup belongs here.

5. **New features — payoff planner, charts, subscriptions, budget targets**
   - Depend on the core data layer being stable.
   - `chartsController.js` calls Plotly.js; requires data services to be clean first.

6. **Integrations — PDF parser, cloud sync**
   - Most complex; highest risk.
   - PDF parser is entirely self-contained — build and test independently.
   - Cloud sync requires HTTPS hosting — develop against GitHub Pages, not file://.

| Service | Integration Pattern | Notes |

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| Controller ↔ Service | Direct function call (ES6 import) | No event bus needed at this scale |
| Service ↔ db | Direct Dexie method calls | Services are the only callers of db methods |
| Service Worker ↔ App | `postMessage` (if update available) | vite-plugin-pwa handles this via prompt-for-update |
| PDF Parser ↔ Controller | Returns array of candidate transactions | Controller shows preview; does not auto-insert |
| Sync Service ↔ db | Calls same export/import functions as manual backup | Sync is just a transport layer on top of JSON backup |

## Anti-Patterns

### Anti-Pattern 1: God Controller

**What people do:** Put calculation logic inside controllers to avoid creating service files.
**Why it's wrong:** The monolith is the direct consequence of this. Debt calculation appears in two places with different results. Testing requires a browser.
**Do this instead:** Controllers own only: read form → call service → render result. No arithmetic in controllers.

### Anti-Pattern 2: Calling `refreshAll()` Everywhere

**What people do:** After every change, re-query and re-render every table.
**Why it's wrong:** At 1,000+ records, querying all tables on every keystroke is noticeably slow. The existing monolith already does this and it is listed as a known performance problem.
**Do this instead:** Track which data changed. Call `renderDashboard()` and the specific table's render function. Only call all renders on initial load.

### Anti-Pattern 3: Storing Access Tokens in IndexedDB

**What people do:** Persist OAuth access tokens alongside app data for convenience.
**Why it's wrong:** IndexedDB contents are readable by any JavaScript on the same origin. Access tokens should be short-lived and in memory only (or refresh tokens in localStorage with awareness of the risk).
**Do this instead:** Keep access tokens in module-scope variables (memory). Store only the long-lived Dropbox refresh token in localStorage, with a comment explaining the risk.

### Anti-Pattern 4: Hard-Coding PDF Column Pixel Values

**What people do:** Inspect one Barclays PDF, note that the "Amount" column is at x=480, and hard-code that.
**Why it's wrong:** Column positions shift between statement dates, paper sizes, and PDF generators. The parser breaks silently on any variation.
**Do this instead:** Detect column positions from the header row on each parse run. Hard-code header text signatures, not coordinates.

### Anti-Pattern 5: Loading pdfjs-dist from CDN in a PWA

**What people do:** Use `<script src="https://cdnjs.cloudflare.com/ajax/libs/pdf.js/...">` for convenience.
**Why it's wrong:** The service worker precaches known assets. CDN scripts are not in the precache manifest, so the app fails offline.
**Do this instead:** Bundle `pdfjs-dist` with Vite. The worker chunk will be included in the precache automatically.

## Scaling Considerations

This is a personal-use local-first app. Scaling is framed around data volume, not user count.

| Scale | Architecture Adjustments |
|-------|--------------------------|
| < 5,000 transactions | Current design — load all records, filter in memory |
| 5,000–20,000 transactions | Add `.limit()` and `.offset()` to renders; paginate variable spends table |
| > 20,000 transactions | Add year-based archival table; load only current year by default |

### Scaling Priority

1. **First bottleneck:** `variableSpends` table with thousands of transactions rendered as DOM rows. Fix: paginate with 100 rows per page and a "Load more" button.
2. **Second bottleneck:** Payoff simulation with 10+ debts runs noticeably slowly. Fix: early termination when all debts paid, memoize interest per month. (600-month loop with 10 debts = 6,000 iterations — acceptable; with 50 debts = 30,000 — slow.)
